## 신호가 있는 것 vs 없는 것 — 이 구분이 제품의 자리다

### 자동 (hipify, 164줄)
API 이름 치환, 헤더 경로 대부분, 런타임 타입, 커널 런치 문법.
→ **공짜 도구가 이미 한다. 여기엔 사업이 없다.**

### 신호가 있는 16건 — LLM 루프가 자동으로 수렴한다

컴파일러가 파일·줄·증상을 알려준다. 고치고 다시 컴파일하면 남았는지 없어졌는지 즉시 안다.
**19건 전부 LLM 이 고쳤다.** 사람이 손으로 고쳐야 하는 건 없었다.

| 종류 | 건수 | 예 |
|---|---|---|
| HIP 에 API 가 없음 | 5 | `cg::reduce` 심볼 0건 · `__stcs` 전무 · `__syncwarp` 부재 |
| 헤더 경로·이름 | 4 | ROCm 5.x 평면 경로 · `<cuda_bf16.h>` · `hip/hip_runtime.h` |
| 타입·오버로드 | 3 | `min(int, unsigned)` · 호스트 `isfinite` · `memset` 이 `__device__` |
| 전처리기 조건에 숨은 정의 | 1 | `__CUDACC_VER_MAJOR__` 가드로 bf16 정의가 통째로 사라짐 |
| ROCm 버전 간 차이 (6.3 → 7.0.2) | 2 | `__syncwarp` 중복 정의 · `..._v2` API 제거 |
| 환경 | 1 | 이미지에 hipBLAS 미설치 |
| 런타임 에러 코드 | 1 | `hipblasSetMathMode(TF32)` → `NOT_SUPPORTED(7)` |

> **부수 발견: "NVIDIA → AMD" 가 끝이 아니라 "AMD 버전 간" 이식이 또 있다.**
> ROCm 6.3 에 없어서 우리가 채운 `__syncwarp` 가 7.0.2 에서는 중복이 됐고,
> 반대로 있던 API 하나는 사라졌다. 방향이 양쪽이다.
> 고객 입장에서는 **ROCm 을 올릴 때마다 다시 깨진다**는 뜻이다.

### ★ 신호가 없는 3건 — 여기서 루프가 멈춘다

컴파일 통과 · 크래시 없음 · **답만 틀림.** 재컴파일해도 아무 변화가 없어서
**LLM 이 "고쳤는지"를 판단할 근거가 없다.**

**1. 호스트 `max(float, float)` 가 `int max(int, int)` 로 해석됨**
```c
max_el = max(max_el, out[i]);      // 호스트 코드
```
HIP 호스트에는 float 오버로드가 보이지 않는다. float 가 int 로 변환되고 `-inf` 는
UB 라 쓰레기값(905987520)이 나온다. CUDA 는 호스트에도 오버로드가 있어 원본은 정상이다.
실측: 호스트 `is_int=1` / 디바이스는 정상.
경고 한 줄(`argument has type 'int'`)만 나오고 **원본에 우연히 있던 `assert` 가 유일한 방어선이었다.**

**2·3. 커널 8 — 웨이브 폭 가정이 디바이스·호스트 양쪽에**
```c
// 디바이스
const int warpsPerBlock = blockDim.x / warpSize;   // NVIDIA 32/32=1 · AMD 32/64=0
int row = blockIdx.x * warpsPerBlock + warpId;     // AMD 에서 전부 0
// 호스트
const int grid_size = ceil_div(N * 32, block_size); // "행 하나당 32스레드" 전제
```
**둘 중 하나만 고치면 여전히 틀린다.** 실제로 첫 수정 후에도 `block_size=64` 에서 실패했다.

### ★★ 일괄 치환이 불가능한 이유 — 가장 명확한 증거

같은 파일, **글자까지 동일한 두 줄**인데 한쪽은 맞고 한쪽은 틀리다.

```c
void softmax_forward_online2(...) {                      // 커널 6
    const int grid_size = ceil_div(N * 32, block_size);  // ✅ 옳다
}   // 커널 안: cg::tiled_partition<32>  ← 32레인 타일을 명시

void softmax_forward_online8(...) {                      // 커널 8
    const int grid_size = ceil_div(N * 32, block_size);  // ❌ 64 여야 한다
}   // 커널 안: blockDim.x / warpSize   ← 런타임 값 사용
```

어느 쪽이 틀렸는지는 **각 커널이 스레드를 어떻게 배치하는지 읽어야만** 알 수 있다.
문자열 치환으로는 도달할 수 없고, `sed` 로 일괄 처리하면 **맞는 쪽을 망가뜨린다.**

### 변환 불가 / 재작성 필요
cuDNN Flash Attention (attention 커널 10·11) — ROCm 에 1:1 대응 없음.
`ENABLE_CUDNN` 기본 비활성이라 이번 범위에서는 자동 제외됐다.

## 그래서 제품이 무엇인가

이번 작업의 실증은 두 문장으로 요약된다.

1. **공짜 도구는 164줄을 해준다. 그다음 19건이 남는다.**
2. **19건 중 16건은 LLM 이 자동으로 수렴시킬 수 있다. 남은 3건은 정답 대조 없이는 발견조차 안 된다.**

제품은 "뛰어난 전문가"가 아니다. **점검-개선 루프를 LLM 으로 자동화하는 것**이고,
그 루프가 돌기 위한 **종료 조건을 고객이 이미 갖고 있는 NVIDIA 결과물로 만드는 것**이다.

우리 하네스가 내는 줄이 정확히 그 종료 조건이다:
```
[RESULT] kernel=flash_attention_fwd status=PASS max_rel_err=1.815e-06 ...
```
`status=FAIL` 이면 루프를 한 번 더, `PASS` 면 멈춘다. 사람이 읽는 리포트가 아니라
**루프의 종료 조건**이다.

고객이 자기 워크로드의 NVIDIA 출력을 넣으면 이 줄이 자동으로 생성된다.
→ 설계: [demo-plan.md](demo-plan.md) 장치 1·2

## 부수 발견 — llm.c 자체의 결함

이식 작업과 별개로 원본 코드에서 두 가지를 찾았다.

1. **fp32 경로가 컴파일되지 않는다.** `common.h` 의 `#else`(fp32) 분기가
   `CUBLAS_LOWP` / `CUBLAS_LOWP_COMPUTE` 를 정의하지 않는데 `attention_forward` 가 11곳에서 쓴다.
   `ENABLE_BF16` 을 끄는 순간 드러난다. (NVIDIA·AMD 양쪽에서 동일하게 발생)
2. **flash 예제 커널의 divergent `__syncthreads()`** — `if (row >= N) return;` 뒤에 배리어가 있어
   N 이 블록 크기의 배수가 아니면 정의되지 않은 동작이다.

## 방법론 (숫자를 신뢰할 수 있는 이유)

- llm.c 내장 `validate_result`(tol 1e-4) · `benchmark_kernel` 을 그대로 사용. 자체 판정 아님
- flash 커널은 별도 하네스 — CPU 레퍼런스 double 누적, **결정적 난수**로 양 플랫폼 입력을
  비트 단위 동일하게 고정 (libc `rand()` 는 구현마다 달라 쓰지 않았다)
- 수정 전 hipify 원본 출력을 커밋해 두고 이후 diff 를 "사람이 한 일"로 계측
- llm.c 커밋 `f1e2ace6` 고정 · 컴파일 플래그 양쪽 동일 (`-O3` + fast-math)
- MI300X 세션을 **두 번** 돌려 같은 값이 나오는지 확인했다 (`1.815e-06` / `98.8 GFLOP/s` 동일)

## 한계 (선제적으로 밝힌다)

### ★ 성능 비교는 하지 않는다 — 이번 프로젝트의 범위가 아니다

기준선이 **GTX 970 (2014년, 3.5 TFLOPS)** 이고 MI300X 는 163 TFLOPS 다.
24~47배의 하드웨어 격차를 이식 품질로 발표하면 신뢰도가 무너진다.

동급 NVIDIA(H100/H200) 를 빌려 재측정하는 방안은 **비용 대비 얻는 것이 없다고 판단해 접었다.**
이 프로젝트가 증명하려는 것은 "AMD 가 빠르다"가 아니라 **"이식이 맞는지 자동으로 검증된다"** 다.
성능은 이식이 맞은 다음에 오는 별개의 과제다.

측정된 시간은 `03-verify/comparison.md` 에 참고용으로만 남긴다. **발표 자료에 넣지 않는다.**

### 그 밖의 한계

- 전 구간 **fp32** 다 (기준선 GPU 가 bf16 미지원). 저정밀 경로는 범위 밖
- 문제 크기를 **B=2** 로 줄였다 (Windows TDR 제약). MI300X 도 동일 조건으로 맞췄다.
  **B=2 는 MI300X(304 CU) 를 채우기엔 너무 작다** — 성능을 논할 수 없는 또 하나의 이유다
- 커널 단위 비교이며 학습 전체 파이프라인이 아니다
- MI300X 튜닝은 하지 않았다 — 이식성 측정이 목적이지 최적화가 아니다
- **표본은 3파일 2,294줄이다.** 19건·3건이라는 숫자를 산업 전체로 외삽하지 않는다.
  설득력은 비율이 아니라 **그 3건의 성격**에 있다
